Bunching, Journaling, and scaling__________________________________________

We perceive the world as a hierarchy and is the natural way for viewing data.
The interface to the system needs to be hierarchal and/or based on a time series of captured measurements
	But even in the timeseries, measurements belong to some component
	Statistics dependent on our ability to roll up statistics through a hierarchy
		We need to know which sensor belongs to which component (metadata) and, in turn, what that component belongs to, and so on 

"At the time we started we could only do I/O when we opened the database."

As stress on the system increases -- as more activities pile up -- the system bunches the activities
It's the number of bunches that matters, less so the number of activities in each bunch

Invoking a subroutine has costs in saving and restoring context
If you're going to a subroutine, you should bunch activities for the subroutine to perform

XRF, RAID 5, and Recovery__________________________________________________________________

RAID 5
Need to cover striping and XOR or just making copies

If data is added to the journal as it happens, it's not the right order
Better: If the journal is a timeseries that organizes related actions (records that look similar)

So we have sensors that record what happens in a time series that groups adjacent records
	Record size reduced by a factor by 30 times
	Matters because, potentially, millions of records

IMS introduces had two approaches towards writing 
	write a temporary journal record, oriented towards response time
		Don't mind if the header is large because it's not kept around for long
		Log Write Ahead in the ledgers
	write the final journal record, oriented towards throughput (group commit)
		Group commit

Throughput (and reliability) is further improvement by using RAID 5 -- writing out in parallel to stripes
	Can be hundreds of times faster than the disk speed
	XOR operations in real time can recreate any lost stripe

If you then write to another site a 100 miles away, you have disaster recovery
	XOR to regenerate any missing data

Message back to the user was sent when the transaction was recoverable

Justification for Escrow

For online statistics/online aggregates (e.g. cash flow in individual accounts, cash flow for the bank): hot spots
Update these aggregates with each transaction 
	If you are doing a lock, read current value, (modify), update, release lock
		Which would limit you to 10 transactions per second
So, instead, move to just changing the cumulative value
	Ignore the sequence of transactions and just change the cumulative value

This is key: Works just as well for quantity on hand for !!any!! inventory
	Provided all the items in that inventory are identical)
		Wouldn't work, for example, for seats on a plane unless you don't assign seats
		Does work for a bank account where all money looks alike
So the Validate and Update single operation: 
	Got up to 100 transactions per second on a single record
